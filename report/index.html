03 / Toolchains

官方工具优先，通用工具留作备选

04 / Deployment pipeline

从 FP32 基线到可上机器人的 INT8 固件

每一步都保留可比较产物，避免在量化、转换和控制逻辑同时变化时失去问题定位能力。

固定 FP32 基线

记录 ONNX 输出、仿真奖励、摔倒率和关键动作轨迹。

采集校准数据

保存真实 rollout 的 61 维观测，覆盖行走、转向、静止和扰动。

图简化

标准化移到固件侧；确认 FC 与激活的目标算子映射。

PTQ / QAT

先做 INT8 PTQ；闭环退化时再用 QAT 微调。

板上集成

静态分配内存，将推理嵌入 50 Hz 传感器与舵机循环。

逐级放行

离线对齐 → 仿真闭环 → 吊架低功率 → 自由行走。

不可省略：当前导出器把 observation normalizer 烘焙进 ONNX。若 MCU 将它移出模型，必须逐项保存并复现相同的 mean、std、裁剪规则与观测顺序；否则即使网络权重完全正确，策略也会立即失效。

05 / Risk register

优先处理会让机器人摔倒的问题

风险按闭环影响排序。文件大小不是最高风险；观测契约或时序错误会让一个离线 MAE 很低的模型仍然无法行走。

观测契约偏差

61 维顺序、单位、关节方向、上一动作或标准化任一不一致，都会形成系统性错误。

对策：保存黄金观测向量，逐元素对比 Linux 与 MCU。

ELU 量化与回退

目标工具可能不支持高效 INT8 ELU，或静默回退到慢速浮点实现。

对策：先跑转换器分析；必要时训练 ReLU 版本。

20 ms 最坏延迟

平均推理快不代表控制可靠；舵机总线、IMU 与偶发中断会共同占用预算。

对策：统计 P99.9 与最大周期，并设置超时安全态。

PTQ 校准覆盖不足

只用直行样本会让转向、跌倒边缘状态的激活范围发生饱和。

对策：按行为分桶采样，并记录每层饱和率。

连续动作量化误差

单步小误差进入 50 Hz 闭环后可能表现为抖动、漂移或能耗上升。

对策：比较动作 MAE 之外，还要做长时闭环仿真。

模型存储容量

INT8 权重约 193 KiB，可放在常见 ESP32-S3/STM32 的 Flash 中。

对策：权重留 Flash，内部 SRAM 优先给激活和实时缓冲。

06 / Acceptance gates

四道门，不能只看“能跑起来”

具体阈值应在 FP32 rollout 上建立分布后冻结。下面定义的是必须测量的维度，而不是未经实验的万能数值。

A

逐张量一致性

黄金输入上核对标准化结果、各层输出、最终 14 维动作和限位后的目标位置。

B

离线误差

统计动作 MAE、最大误差、P99 误差、余弦相似度和 INT8 饱和比例。

C

闭环行为

比较速度跟踪、摔倒率、关节抖动、能耗代理指标和不同命令区间表现。

D

板上实时性

测量完整周期最大值、P99.9、内存峰值、看门狗触发和通信丢帧。

07 / Recommendation

先用工具降低不确定性，再定硬件

这不是单纯的格式转换任务，而是把一个对时序和观测非常敏感的闭环控制器迁移到资源受限平台。

推荐的第一条路线 STM32H7
+ Cube.AI

理由不是算力更强，而是可以先直接分析现有 ONNX，快速得到算子、Flash、RAM 和延迟证据。待模型图与 INT8 行为稳定后，再平移到 ESP32-S3。

建议的下一阶段交付物

  1. 从仿真采集按行为分桶的 61 维校准集和 FP32 黄金输出。
  2. 生成“标准化在模型外”的 ONNX，并确认与当前 ONNX 数值等价。
  3. 分别跑 STM32Cube.AI 分析和 ESP-DL/ESP-PPQ 转换，记录不支持算子。
  4. 制作 INT8 PTQ 候选；若闭环退化，再训练 ELU-QAT 或 ReLU-QAT 版本。
  5. 在两块开发板运行同一黄金测试集，形成延迟、Flash、RAM、误差对比表。
